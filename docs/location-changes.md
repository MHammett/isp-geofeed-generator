# Guard against unintended location changes

A prefix can stay in the feed while a bad site edit moves all of its addresses to another
city. Withdrawal checks do not catch that. The location-change guard compares the previous
published location data with the candidate before any built-in output writes or replaces
its recovery backup.

`max_relocated_fraction` defaults to `0.10`. More than 10% changed location coverage stops
publication. Set `0` to stop any location change. IPv4 and IPv6 are measured separately.
The count uses addresses, not CSV/JSON rows, so splitting or combining equivalent prefixes
does not create a false move. Exactly the configured limit is allowed.

Only addresses present in both feeds have a location to compare. The fraction is changed
addresses divided by those retained addresses. Removing other space does not dilute that
fraction: if half a prefix is removed and the remaining half changes city, the location
change is 100% of retained coverage. Withdrawal limits apply separately.

Newly added space and a first publication have no earlier location baseline. They still
need normal source selection, site/location validation, allowed allocations and current
fullbogon checks. A missing source or selected record still stops the run.

## What counts as a change

CSV compares country, region and city. Rich JSON compares all published location fields,
including latitude/longitude, postal code and accuracy. Adding or removing fields from
the output profile also counts as changed location data. A coordinate change counts even
if small; the tool does not infer a distance, geocode a city or guess equivalence.

Normal text trimming and Unicode normalization avoid changes caused only by equivalent
text encodings. City names remain case-sensitive. Equivalent numeric forms, such as 1 and
1.0, compare equal. Locations are compared across exact prefix intersections with integer
address counts, including very large IPv6 ranges.

The guard's error names the address family, changed percentage of retained coverage and
limit. It shows two decimal places; a smaller nonzero change appears as `<0.01%`.
Nonzero remainders are marked as rounded down. Display rounding never changes enforcement:
the guard compares exact integer coverage, including a single IPv6 address above a limit.
It does not dump
city names, coordinates or customer records. A stopped run keeps the public bytes and the
prior recovery backup intact. Candidate generation validates data, but does not claim a
comparison with the currently published baseline.

## Review and approve an intended change

Keep the schedule stopped while investigating a blocked move. Generate a private candidate
and compare it with the last good feed and the source's intended service locations. Check
which prefixes changed, why they changed and whether their sites are correct. This is an
operational data review, not a code review.

Use the same configured interpreter, service account and credential backend as the normal
run. The following bash examples assume the CLI package is installed in that environment:

```bash
isp-geofeed-generator generate --config /etc/isp-geofeed-generator/config.yaml --output /var/lib/isp-geofeed-generator/review/candidate.csv
```

After reviewing the candidate, copy its printed lowercase SHA-256 into the one-off publish
command. In bash, replace the placeholder with that exact 64-character hash:

```bash
isp-geofeed-generator publish --config /etc/isp-geofeed-generator/config.yaml --approve-location-changes REVIEWED_SHA256
```

The same options work with Python's module command on Windows. For systemd-encrypted
credentials, use a one-off service with the normal unit's User, environment, config and
LoadCredentialEncrypted settings. Append the approval option only to that reviewed run.
Do not put credentials into arguments or change the normal scheduled command.

If live source data has changed since the review, the generated bytes will have a different
hash and no write occurs. Generate and review again. A matching hash permits location
changes for that exact candidate only. It does not bypass bogon, ownership, overlap,
withdrawal, output field, concurrency, public read-back or recovery checks. A successful
approved run records the hash in private status as `location_change_approval_sha256`.

Leave the normal threshold in place for subsequent runs. If the move was wrong, correct
the source or private mapping first. Restore the prior approved package/config only when
that is the intended recovery; older versions do not provide this protection. A package
rollback is not permission to publish a changed location.

## Output extensions

File, WordPress and rich JSON publishers enforce the guard using their actual prior state.
SDK publishers accept `max_relocated_fraction` alongside `max_removed_fraction`. Existing
targets that delegate with `**guards` receive it without an entry-point version change.
Targets with their own transport must read prior state and enforce both guards before a
write; `sdk.relocation_guard(previous_records, candidate_records, limit)` is available for
normalized records. Forward the guard arguments when wrapping a checked SDK publisher.

Enabled extensions remain trusted code. The core cannot certify a custom target that ignores
its output contract. Re-test local extensions before updating; installed-wheel tests cover
an external target refusing a move and accepting only the reviewed candidate hash.
